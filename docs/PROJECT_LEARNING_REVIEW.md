# 个人项目学习复盘

这份文档是给我自己复盘用的，不是给下一届负责人日常维护用的。它记录这个篮球队官网到底做了什么、用了哪些技术、上线过程中学到了什么，以及后续如果继续提升，可以沿着哪些方向学。

本文不记录真实后台密码、`SESSION_SECRET`、服务器登录密码、SSH 私钥或任何账号密码。

## 1. 项目整体介绍

### 这个网站解决了什么问题

这个项目解决的是“篮球队需要一个可以公开展示、也能自己维护内容的官网”的问题。

它不是一个只放几张图的静态页面，而是一个带后台的球队官网。前台面向学院师生、新队员、球队负责人和潜在赞助方，展示球队资料、队员阵容、赛程战绩、新闻动态、影像素材、招新信息和赞助合作信息。后台面向球队负责人，用来更新这些内容、上传图片/视频、查看报名记录。

项目最终已经部署到香港 VPS，通过公网 IP 可以访问，并且完成了 pm2、Nginx、静态缓存、视频 Range、自动备份和交接文档整理。

### 当前项目包含哪些主要功能

- 首页展示球队介绍、近期动态、队员风采和关键数据。
- 球队页展示球队简介、训练安排和荣誉。
- 赛程战绩页展示比赛时间、对手、比分和结果。
- 新闻列表和新闻详情页展示球队动态。
- 队员阵容页和队员详情页展示球员资料、照片、标签和雷达图。
- 影像中心展示比赛照片、比赛视频、赛后合照、训练和球队生活。
- 招新页支持球员报名和运营报名。
- 赞助页展示合作伙伴和赞助详情。
- 联系页展示球队联系方式。
- 后台支持登录、内容编辑、保存、图片/视频上传、报名记录管理。
- 线上自动备份运行时数据和上传素材。

### 前台和后台分别负责什么

前台负责“给访问者看”。它展示公开内容，例如队员、赛程、新闻、照片、视频、招新说明和赞助信息。前台主要通过 `GET /api/site` 读取公开数据，报名记录不会暴露给前台。

后台负责“给维护者改”。维护者登录 `/admin` 后，可以读取后台数据、编辑内容、保存全部、上传素材、查看和处理报名记录。后台接口需要登录 token，例如 `GET /api/admin/site`、`PUT /api/admin/site`、`POST /api/admin/upload`、`GET /api/admin/applications` 等。

## 2. 技术栈总结

### 前端：原生 HTML、CSS、JavaScript

它是什么：
HTML 负责页面结构，CSS 负责样式，JavaScript 负责页面渲染、路由切换、后台交互和 API 调用。

在本项目里具体干什么：
`public/index.html` 是前台和后台共用的入口；`public/styles.css` 是全站样式；`public/app.js` 负责前端路由、页面渲染、后台表单、登录、保存、上传、报名提交等逻辑。页面不是由 Vue、React 或 Next.js 做的，而是原生 JS 根据当前路径渲染对应页面。

为什么需要它：
这个项目功能规模适中，用原生前端能减少构建复杂度，不需要额外前端打包工具。上线时不用生成 dist 目录，只要 Node 服务能提供 `public/` 里的文件即可。

### 后端：Node.js 内置 HTTP Server

它是什么：
Node.js 可以在服务器上运行 JavaScript。内置 HTTP Server 可以直接创建 Web 服务，接收浏览器请求并返回页面、JSON 或文件。

在本项目里具体干什么：
`server/server.mjs` 创建 HTTP 服务，处理公开 API、后台登录、后台保存、文件上传、报名提交、报名管理和本地静态文件访问。

为什么需要它：
如果只是纯静态网站，后台保存、报名、上传都做不了。Node 服务让这个官网具备“可维护、可写入、可上传”的能力。

### 数据存储：JSON 文件

它是什么：
JSON 是一种文本格式，可以保存结构化数据。项目没有使用 MySQL、PostgreSQL、MongoDB 等数据库。

在本项目里具体干什么：
`data/site-data.seed.json` 是上线初始内容快照；线上真实运行时数据是服务器上的 `data/site-data.json`。后台点击“保存全部”后，公开内容会写入这个 JSON 文件；报名记录也保存在同一个数据文件里，但不会通过公开 API 暴露。

为什么需要它：
对一个学院球队官网来说，数据量不大，维护人数少，JSON 文件更简单、部署成本低。缺点是多人同时编辑时容易互相覆盖，长期运营可以再升级数据库。

### 图片和视频管理

它是什么：
图片、视频属于网站媒体素材。图片适合压缩成网页友好的格式；视频通常较大，需要谨慎处理。

在本项目里具体干什么：
图片主要在 `public/assets/` 下，当前部署图片多为 WebP。后台上传图片时，服务端用 `sharp` 转成 WebP，并限制最大边到 1920px。视频是 MP4 等文件，不进入 GitHub，通过服务器同路径单独上传。重点大视频已经生成 `-web.mp4` 网页播放版并切换，原视频保留。

为什么需要它：
官网视觉内容很多，如果图片和视频不管理，页面会慢、仓库会巨大、服务器也难迁移。图片压缩、视频不进 Git、重点视频生成网页播放版，是让网站能长期维护的关键。

### sharp

它是什么：
`sharp` 是 Node.js 里的图片处理库，可以压缩、裁剪、转换图片格式。

在本项目里具体干什么：
后台上传图片后，`server/server.mjs` 会调用 `sharp` 自动旋转、限制尺寸，并输出 WebP。这样负责人上传 jpg/png/webp 都可以被统一优化。

为什么需要它：
普通负责人上传的图片可能很大。如果不处理，网页加载慢，服务器空间也容易被占满。自动压缩能减少人工处理成本。

### GitHub

它是什么：
GitHub 是代码仓库平台，用来保存项目代码、文档和版本历史。

在本项目里具体干什么：
本项目代码和文档同步到 GitHub。VPS 通过 GitHub Deploy key 拉取仓库。需要注意的是，GitHub 保存的是代码和文档，不保存真实密码、线上运行时数据、后台上传目录和大视频。

为什么需要它：
GitHub 让项目有版本记录，方便回滚、交接和后续维护。下一届负责人可以从 GitHub clone 最新代码，而不是靠压缩包传来传去。

### VPS

它是什么：
VPS 是云服务器。它是一台长期在线的 Linux 服务器，可以运行 Node 服务、保存数据和对外提供访问。

在本项目里具体干什么：
项目部署在香港 VPS，目录是 `/var/www/basketball-team-website`。Node 服务、pm2、Nginx、运行时数据、上传文件、视频文件和自动备份都在这台服务器上。

为什么需要它：
这个项目不是纯静态网站，需要后台写入和文件上传，所以需要一台有持久磁盘、能长期运行 Node 的服务器。香港 VPS 还能减少备案压力，适合快速上线。

### Nginx

它是什么：
Nginx 是常见 Web 服务器和反向代理。它可以接收公网请求，再转发给 Node，也可以直接高效提供静态文件。

在本项目里具体干什么：
Nginx 对外监听 80 端口，把页面和 API 请求转发到本机 Node 服务；同时让 `/assets/` 由 Nginx 直接托管并设置缓存。这样图片和视频不必全部经过 Node。

为什么需要它：
Node 专心处理动态 API，Nginx 专心处理公网入口和静态资源，性能和稳定性更好。视频文件由 Nginx 托管，还能更好支持 Range 分段请求。

### pm2

它是什么：
pm2 是 Node.js 进程管理工具，可以让 Node 服务常驻运行，并在服务器重启后恢复。

在本项目里具体干什么：
线上服务名是 `basketball-team-website`。pm2 负责启动 `server/server.mjs`，查看状态、查看日志、重启服务和开机自启。

为什么需要它：
如果直接用命令行运行 Node，关掉终端或服务器重启后服务就可能停掉。pm2 让网站更像正式服务，方便维护。

### 自动备份脚本

它是什么：
自动备份脚本是一个 Bash 脚本，用来定期把重要运行时数据打包保存。

在本项目里具体干什么：
`scripts/backup-runtime.sh` 默认备份 `data/site-data.json`、`public/assets/uploads` 和 `public/assets/gallery/**/*-web.mp4`。线上通过 crontab 每天凌晨 3:30 执行，备份到 `~/basketball-backups`，默认保留 14 天，并生成 `.sha256` 校验文件。

为什么需要它：
后台保存的内容和上传文件不在 GitHub 里。如果服务器误删、迁移失败或数据被覆盖，没有备份就很难恢复。备份保护的是线上真实运营数据。

## 3. 项目目录结构讲解

### `public/`

这是浏览器能访问到的前端目录。`index.html` 是页面入口，`app.js` 负责渲染前台和后台，`styles.css` 负责样式。无论访问首页、新闻页、队员页还是后台页，最终都是前端 JS 根据路径渲染内容。

### `public/assets/`

这是网站实际使用的公开素材目录，包括球队照片、新闻封面、球员照片、影像中心图片和视频等。线上 Nginx 已经把 `/assets/` 直接托管并开启缓存，所以这里的文件访问效率更高。

### `data/`

这是数据目录。`data/site-data.seed.json` 是 GitHub 中保存的上线初始数据快照。线上真实数据是服务器上的 `data/site-data.json`，这个文件会被后台保存更新，但不提交到 GitHub。

### `server/`

这是后端目录。`server/server.mjs` 是核心服务，负责 API、登录、上传和静态文件兜底。`server/dataStore.mjs` 负责读取和写入 JSON 数据。`server/defaultData.mjs` 是内置兜底数据。`server/seedData.mjs` 负责读取 seed 快照。

### `scripts/`

这是脚本目录。`build-check.mjs` 用来检查数据结构和脚本语法；`optimize-existing-assets.mjs` 用来批量优化已有图片；`backup-runtime.sh` 是线上自动备份脚本。

### `docs/`

这是文档目录。它包含交接文档、运维命令、内容维护说明、部署记录、优化记录、备份说明、域名 HTTPS TODO、视频优化记录和这份个人复盘文档。项目能交接顺利，主要靠这里的文档说明清楚。

### `package.json`

这是 Node 项目的配置文件。里面定义了项目脚本：

```text
npm start  启动 Node 服务
npm run build  运行数据和脚本检查
npm test  运行自动测试
```

它还记录依赖，目前主要依赖是 `sharp`。

### `package-lock.json`

这是依赖锁定文件。它记录安装依赖时的具体版本，避免服务器和本地安装出不同版本导致问题。

### `README.md`

这是项目入口说明。它告诉后续负责人项目当前状态、阅读顺序、关键目录、不能提交到 GitHub 的内容，以及本地运行方式。

### `.gitignore`

它告诉 Git 哪些文件不要提交。当前忽略了 `data/site-data.json`、`node_modules/`、日志、本地原始素材库、大视频和上传目录。这是保护仓库体积和敏感运行时数据的重要文件。

### `tests/`

这是自动测试目录。测试覆盖数据初始化、后台 API、上传、报名、视觉关键契约等。每次重要修改后运行 `npm test`，能减少上线后出问题的概率。

### 本地原始素材库

`球员照片`、`影像素材`、`球队名单.xlsx` 是本地原始资料，不作为正式网站访问目录，也不提交到 GitHub。它们适合本地归档，不适合直接部署给用户访问。

## 4. 核心代码逻辑讲解

### 网站页面是怎么加载内容的

浏览器打开网站后，先加载 `public/index.html`，再加载 `public/app.js`。前端 JS 会请求：

```text
GET /api/site
```

后端读取当前数据文件，并通过 `publicSiteData()` 去掉 `applications` 报名记录，只返回公开网站数据。前端拿到数据后，根据当前路径渲染首页、队员页、新闻页、影像页等。

这就是为什么后台保存后，前台能刷新看到新内容：前台不是写死的 HTML，而是从 JSON 数据渲染出来的。

### 后台登录大概是怎么实现的

后台登录接口是：

```text
POST /api/login
```

前端把用户输入的密码发给后端。后端把它和 `ADMIN_PASSWORD` 环境变量中的密码比较。登录成功后，后端用 `SESSION_SECRET` 生成一个带过期时间的 token，有效期是 12 小时。前端把 token 存到浏览器 `localStorage`，之后访问后台接口时带上：

```text
Authorization: Bearer token
```

当前项目没有多账号系统，只有单管理员密码。

### 后台保存内容是怎么写入数据文件的

后台读取内容用：

```text
GET /api/admin/site
```

后台保存内容用：

```text
PUT /api/admin/site
```

保存时，前端把后台编辑后的公开数据整体发给后端。后端会先读取当前数据，保留原来的 `applications` 报名记录，再把公开内容写回 `data/site-data.json`。真正写文件的逻辑在 `server/dataStore.mjs` 里，使用 `writeFile` 把 JSON 格式化后保存。

这也解释了一个限制：当前是“保存全部”，多人同时编辑时可能互相覆盖，所以长期运营可以考虑拆成模块保存或使用数据库。

### 图片/视频上传后如何被前台引用

后台上传接口是：

```text
POST /api/admin/upload
```

上传时需要后台 token。后端会检查文件扩展名，只允许 jpg、jpeg、png、webp、mp4、webm、mov。图片会用 `sharp` 转成 WebP，视频则原样保存。文件会写入：

```text
public/assets/uploads/<context>/
```

后端返回一个网站路径，例如：

```text
/assets/uploads/gallery/xxxx-team-photo.webp
```

前端把这个路径填到后台字段里。维护者还要点击“保存全部”，这个路径才会写入 `data/site-data.json`。之后前台根据这个 `/assets/...` 路径显示图片或视频。

### Nginx 为什么要直接托管 `/assets/`

图片和视频是静态资源，访问频率高，文件体积也可能大。让 Nginx 直接处理 `/assets/`，比让 Node 一边处理 API 一边传大文件更合适。

本项目中，页面和 API 仍由 Node 处理；图片、视频、favicon 等静态资源由 Nginx 直接托管并加缓存。这样可以减少 Node 压力，也让视频拖动更稳定。

### 为什么 API 不能缓存

`/api/site` 返回的是网站当前内容。后台保存后，用户应该刷新就看到最新内容。如果 API 被浏览器或代理缓存，前台可能一直拿到旧数据。

所以线上验证过 `/api/site` 返回：

```text
Cache-Control: no-store
```

意思是公开 API 不要缓存，保证后台保存后的内容能及时反映到前台。

### 视频 Range 请求为什么重要

Range 请求允许浏览器只请求视频的一部分，比如从第 10 秒附近开始加载，而不是必须下载完整视频。

对视频播放来说，它很重要：

- 可以拖动进度条。
- 不需要一次下载整个大视频。
- 大视频播放体验更好。

线上已经验证视频 Range 返回 `206 Partial Content`，说明浏览器可以分段请求视频。

### 自动备份脚本如何保护数据

`scripts/backup-runtime.sh` 会生成一个清单，把重要运行时数据打包到 `~/basketball-backups`：

- `data/site-data.json`
- `public/assets/uploads`
- `public/assets/gallery/**/*-web.mp4`

脚本还会验证压缩包能列出内容，并生成 `.sha256` 校验文件。它默认保留 14 天旧备份，避免备份无限堆积。

这个脚本保护的是 GitHub 里没有的东西。代码丢了可以从 GitHub 拉，线上数据和后台上传文件丢了只能靠备份恢复。

## 5. 从 localhost 到线上部署的完整流程复盘

### 本地开发阶段

项目先在本地 `localhost:3000` 跑起来。前台页面、后台页面、数据结构、上传、报名等功能都在本地调试。启动方式可以用 `npm start`，也可以用项目里的启动脚本。

本地开发阶段重点是：页面能正常展示、后台能改内容、数据结构合理、素材路径正确。

### GitHub 上传阶段

项目代码、文档、seed 数据、图片素材和测试被提交到 GitHub。`data/site-data.json`、大视频、上传目录、日志、node_modules、本地原始素材库不进入 GitHub。

GitHub 在这个阶段变成“代码的可信来源”。后续服务器部署和下一届接手都应该从 GitHub 拉最新代码。

### VPS 部署阶段

购买香港 VPS，安装 Ubuntu、git、curl、Nginx、Node.js、npm、pm2 等。服务器通过 GitHub Deploy key 拉取仓库到：

```text
/var/www/basketball-team-website
```

然后执行 `npm install`、`npm run build`、`npm test`，确认服务器环境也能运行项目。

### Node/pm2 启动阶段

在服务器设置环境变量文件：

```text
/etc/basketball-team-website.env
```

里面包含 `ADMIN_PASSWORD`、`SESSION_SECRET`、`PORT`、`DATA_FILE` 等。真实值不写进 GitHub。

然后用 pm2 启动：

```text
pm2 start server/server.mjs --name basketball-team-website --update-env
```

pm2 负责让网站服务长期在线，并支持开机自启。

### Nginx 反向代理阶段

Node 默认监听本机 3000 端口，不直接暴露给公网。Nginx 监听 80 端口，把用户访问转发给 Node。

这样用户访问：

```text
http://43.129.197.63
```

实际由 Nginx 接住请求，再转给 Node 或直接返回静态资源。

### 静态资源缓存优化阶段

上线后优化了 Nginx，让 `/assets/` 由 Nginx 直接托管，并给图片、视频等静态资源设置缓存。API 不缓存，确保后台保存后前台能看到新内容。

这一步让网站访问更快，也让视频文件处理更稳。

### 视频压缩优化阶段

项目里的大视频很多，部分超过 100MB。后续生成了 `-web.mp4` 网页播放版，并把重点大视频切换到网页播放版，例如 `highlight-video-12-web.mp4`。原视频没有删除，方便回滚和归档。

这一步让我理解到：视频不是简单“传上去就完事”，它会影响服务器空间、带宽、用户体验和备份策略。

### 自动备份阶段

上线后新增并启用了 `scripts/backup-runtime.sh`。它每天凌晨自动备份运行时数据、上传目录和 web 视频。手动备份也验证通过。

这一步是为了避免“代码还在，但线上内容丢了”的情况。

### 最终交接阶段

最后整理了 README、HANDOVER、HANDOVER_INFO_TEMPLATE、OPS_COMMANDS、DOCUMENTS_GUIDE 等文档，让下一届能知道：

- 先看哪些文档。
- 网站怎么访问。
- 后台怎么维护。
- 服务器在哪里。
- 备份在哪里。
- 出问题怎么排查。
- 后续 TODO 是什么。

这一步让我意识到，项目交付不是“代码能跑”就结束，能被别人接住才算真正完成。

## 6. 本项目中最重要的工程经验

### 不能把真实密码写进 GitHub

GitHub 是多人协作和长期保存的地方，一旦把密码、密钥、服务器登录信息提交进去，就很难保证不泄露。即使后面删除，Git 历史里也可能还留着。

本项目把真实 `ADMIN_PASSWORD` 和 `SESSION_SECRET` 放在服务器环境变量里，文档只写“通过可信渠道交接”。

### 大视频不适合直接进 Git

Git 适合管理代码和小型文本，不适合管理几百 MB 的视频。大视频进 Git 会让仓库变得很大，clone 慢，历史难清理。

本项目用 `.gitignore` 忽略视频文件，视频单独上传服务器同路径。重点视频再压缩成网页播放版。

### `data/site-data.json` 这类运行数据要谨慎处理

`data/site-data.json` 是线上后台保存后的真实内容和报名记录。如果随便用本地 seed 覆盖它，线上维护的内容可能全部丢失。

本项目把 `site-data.json` 忽略，不进 GitHub；GitHub 只保存 `site-data.seed.json` 作为初始快照。

### 部署前要跑 `npm run build` 和 `npm test`

`npm run build` 会检查数据结构和脚本语法。`npm test` 会跑自动测试，覆盖后台 API、上传、报名、页面关键契约等。

这些检查不是形式主义，它们能在上线前提前发现“页面可能打不开、接口可能坏了、数据结构缺字段”这类问题。

### 要区分“代码文件”和“运行时数据”

代码文件包括 `public/`、`server/`、`scripts/`、`docs/`、`package.json` 等，适合进 GitHub。

运行时数据包括线上 `data/site-data.json`、`public/assets/uploads/`、大视频和备份文件，不适合直接进 GitHub。它们要靠服务器磁盘、手动迁移和备份保护。

### 为什么要做备份

因为上线后真正有价值的不只是代码，还有后台保存的内容、报名记录、上传素材和切换后的 web 视频。代码可以重新拉，运行时数据丢了就很麻烦。

自动备份是防止误删、覆盖、迁移失败的底线。

### 为什么要写交接文档

如果没有交接文档，下一届不知道服务器在哪、后台怎么进、数据在哪里、备份怎么恢复、哪些文件不能删。项目就算能跑，也很难持续维护。

本项目最后整理了文档导航和交接入口，是为了让人接手时少踩坑。

### 为什么上线后还能继续维护和更新

因为内容不是写死在 HTML 里，而是从 JSON 数据读取。后台保存会更新服务器上的 `site-data.json`。所以后续负责人可以通过后台改队员、赛程、新闻、招新、图片等，不需要每次改代码。

如果后续要改页面结构、后台字段、权限系统，那就属于技术开发，需要改代码、测试、提交、部署。

## 7. 常见问题与排查思路

### 网站打不开

先确认是全站打不开还是某个页面打不开。访问 `http://43.129.197.63/`。如果打不开，检查：

- pm2 是否 online：`pm2 status`
- Nginx 是否正常：`sudo systemctl status nginx`
- Nginx 配置是否正确：`sudo nginx -t`
- 服务器磁盘是否满：`df -h`
- 最近是否改过环境变量或 Nginx 配置

### 后台登录不了

先确认后台页能打开：`http://43.129.197.63/admin`。如果页面能打开但登录失败：

- 确认使用的是正式后台密码。
- 确认 `/etc/basketball-team-website.env` 里设置了正确 `ADMIN_PASSWORD`。
- 如果刚改过环境变量，要重启 pm2 并带 `--update-env`。
- 查看 pm2 日志：`pm2 logs basketball-team-website --lines 50`

### 后台保存不生效

先确认后台有没有显示保存成功。然后刷新前台。如果仍然不变：

- 检查线上 `data/site-data.json` 更新时间。
- 检查 pm2 日志有没有写入错误。
- 检查磁盘是否满。
- 确认不是浏览器旧页面缓存；API 已设置不缓存，但可以强制刷新。

### 图片不显示

先看图片路径是否以 `/assets/` 开头。不要用 Windows 本地路径。再检查：

- 文件是否存在于服务器 `public/assets/...`。
- 后台上传后是否点击了“保存全部”。
- Nginx 是否能访问对应 `/assets/...` 路径。
- 图片是否被误删或只存在本地没上传服务器。

### 视频播放卡

视频卡通常和带宽、文件体积有关。检查：

- 视频是否是 `-web.mp4` 网页播放版。
- Range 请求是否返回 `206 Partial Content`。
- 是否多人同时观看导致香港 VPS 带宽压力大。
- 后续是否需要迁移到 COS / OSS / CDN。

### GitHub 代码不是最新

先检查本地：

```text
git status --short --branch
git log -1 --oneline
```

如果本地提交了但 GitHub 没更新，可能是没有 `git push`。如果服务器不是最新，进入服务器项目目录执行 `git pull`，然后根据情况 `npm install`、`npm run build`、`npm test`、重启 pm2。

### pm2 服务掉了

检查：

```text
pm2 status
pm2 logs basketball-team-website --lines 50
```

如果服务不在线，可以按交接文档加载环境变量后重启。服务器重启后如果 pm2 没恢复，可以尝试 `pm2 resurrect`，再检查是否执行过 `pm2 save`。

### Nginx 配置错误

每次改 Nginx 前先备份配置。改完必须执行：

```text
sudo nginx -t
```

只有测试通过才 reload：

```text
sudo systemctl reload nginx
```

如果配置错误，恢复备份文件，再重新测试和 reload。

### 磁盘空间不足

检查：

```text
df -h
du -sh /var/www/basketball-team-website
du -sh ~/basketball-backups
```

常见占空间的是原始大视频、备份文件、上传目录。不要直接删 `site-data.json`、上传目录和正在使用的视频。先确认、备份、再清理。

### 备份没生成

检查：

- `scripts/backup-runtime.sh` 是否存在并有执行权限。
- `crontab -l` 是否有每日备份任务。
- `~/basketball-backups/backup-cron.log` 有没有错误。
- 手动执行 `scripts/backup-runtime.sh` 是否成功。
- 备份目录是否有空间。

## 8. 后续如果想继续提升，可以学什么

### 1. Node.js 后端基础

优先学 HTTP 请求、路由、JSON 解析、文件读写、错误处理、环境变量。这个项目的后端没有框架，适合直接理解 Node HTTP 服务的底层流程。

### 2. HTTP / Nginx / 反向代理

学习请求头、状态码、缓存、Range、反向代理、静态资源托管。理解为什么页面和 API 走 Node，图片和视频交给 Nginx。

### 3. Linux 服务器基础

学习 SSH、目录权限、systemctl、crontab、日志、磁盘空间、进程管理。这个项目的部署和维护都绕不开 Linux。

### 4. Git / GitHub 协作

学习分支、提交、推送、pull、`.gitignore`、Deploy key、敏感信息处理。重点理解什么应该进仓库，什么不应该进仓库。

### 5. Web 安全基础

学习 HTTPS、密码保护、token、登录限速、XSS、文件上传安全、环境变量。当前项目已经做了基本转义和 token，但还可以继续加固。

### 6. 文件上传和数据持久化

学习 multipart 上传、文件类型限制、文件命名、图片压缩、持久化目录、运行时数据迁移。这个项目里的上传和 `site-data.json` 很适合拿来复盘。

### 7. 对象存储 COS/OSS/CDN

如果视频访问量变大，可以学习把大视频迁移到对象存储，并用 CDN 提升播放速度。当前项目未使用 COS/OSS/CDN，只是把它作为后续优化方向。

### 8. 域名和 HTTPS

学习 DNS A 记录、Nginx `server_name`、certbot、证书续期、HTTP 跳 HTTPS。当前项目还没有配置 HTTPS，这是下一届优先 TODO。

### 9. 简单数据库替代 JSON 文件

当前项目未使用数据库。后续可以学习 SQLite、PostgreSQL 或 MySQL，把队员、新闻、赛程、报名记录从 JSON 文件迁移到数据库，解决多人编辑和查询管理问题。

### 10. 多管理员权限系统

当前项目未使用多账号系统。后续可以学习用户表、密码哈希、角色权限、操作日志，让内容维护、报名管理、技术管理分开。

## 9. 我可以怎么向别人介绍这个项目

### 一句话项目介绍

这是一个为学院篮球队做的可维护官网，包含球队展示、新闻、赛程、队员、影像、招新报名、赞助合作和后台管理，并已经部署到香港 VPS 上线运行。

### 技术亮点

- 前端用原生 HTML/CSS/JavaScript 实现多页面路由和后台管理。
- 后端用 Node.js 内置 HTTP Server 提供 API、登录、保存、上传和报名管理。
- 数据用 JSON 文件持久化，适合小团队低成本维护。
- 图片上传自动用 `sharp` 转 WebP，减少网页体积。
- 前台公开 API 不暴露报名记录。
- 自动测试覆盖数据、接口、上传、报名和页面关键契约。

### 部署亮点

- 项目部署在香港 VPS，避免纯静态平台无法持久保存后台数据的问题。
- 使用 pm2 管理 Node 服务，支持常驻运行和重启恢复。
- 使用 Nginx 做公网入口和反向代理。
- `/assets/` 静态资源由 Nginx 直接托管并缓存。
- 视频 Range 已验证，支持分段加载和拖动播放。
- 重点大视频已生成网页播放版并切换，原视频保留。

### 维护亮点

- 后台可以维护队员、赛程、新闻、影像、招新、赞助和报名记录。
- 后台上传图片会自动优化，上传后保存即可给前台使用。
- 自动备份每天执行，保护线上真实数据和上传素材。
- 文档包含交接入口、文档导航、运维命令、内容维护、备份恢复、域名 HTTPS TODO。
- 密码和密钥不写进仓库，只通过可信渠道交接。

### 我从中学到了什么

我学到一个完整项目不只是写页面，还包括数据结构、后台管理、上传、测试、部署、Nginx、pm2、备份、安全、文档和交接。真正上线后，最重要的是让网站能稳定运行、数据不丢、后续负责人能继续维护。

这个项目让我把“本地能跑”推进到了“线上能用、能备份、能交接”的状态。
